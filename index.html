Setup — antes de começar

Faça isto na véspera. No dia, rode o app no navegador (flutter run -d chrome) para não perder tempo com emulador.

flutter --version   # Flutter 3.x instalado?
flutter doctor      # sem erros críticos?
flutter pub get     # dentro da pasta projeto-starter

Rodar em cada plataforma

PlataformaComandoObservação
🌐 Webflutter run -d chromeRecomendado no dia — sem emulador
🍎 iOSflutter run -d iosSimulador (open -a Simulator) ou iPhone conectado
🤖 Androidflutter run -d androidEmulador ou aparelho com depuração USB
🖥️ macOSflutter run -d macosApp desktop nativo

Durante a execução: r = Hot Reload · R = Hot Restart · q = sair. O Hot Reload é o superpoder do Flutter: salve o arquivo e veja a mudança em ~1 segundo, sem perder o estado.

Módulo 1 · Widgets e Layout 40 min

Objetivo: entender que “tudo é widget”, ler a árvore de widgets e criar um widget próprio reutilizável.
Resultado: lista de tarefas com um TaskTile seu e layout organizado — ainda sem interação.

Prática 1 — extraia o TaskTile

No arquivo inicial, cada tarefa é um ListTile jogado dentro da lista. Extraia para um widget próprio (ainda no mesmo arquivo):

class TaskTile extends StatelessWidget {
  const TaskTile({required this.title, super.key});

  final String title;

  @override
  Widget build(BuildContext context) {
    return Card(
      margin: const EdgeInsets.symmetric(horizontal: 16, vertical: 4),
      child: ListTile(
        leading: const Icon(Icons.circle_outlined),
        title: Text(title),
        trailing: const Icon(Icons.chevron_right),
      ),
    );
  }
}

E na lista, troque o ListTile por:

return TaskTile(title: _tarefas[index]);
Atalho: no VS Code, clique sobre um widget e use Cmd/Ctrl + . → Extract Widget. Use o atalho depois de digitar a primeira vez na mão — é digitar que fixa o conceito.

Erro nº 1 de quem começa: remova o Expanded e veja a tela vermelha “Vertical viewport was given unbounded height”. Lista dentro de Column precisa de Expanded — grave isso.

✅ Checkpoint do Módulo 1

Quiz rápido

1. A tela precisa mudar ao tocar num botão: Stateless ou Stateful?

Stateful — ou alguém gerencia o estado por ela (é o Módulo 2).

2. O que o build() recebe e devolve?

Recebe o BuildContext e devolve a árvore de widgets daquela parte da tela.

3. Dei Hot Reload e meu dado sumiu. Por quê?

Provavelmente foi Hot Restart: o Reload preserva o estado, o Restart recria o app do zero.

Módulo 2 · Gerenciamento de Estado 40 min

Objetivo: fazer o app reagir — adicionar, concluir e remover tarefas — e entender onde o estado deve morar.
Resultado: app de tarefas funcionando, com o estado num TaskController fora da tela.

A ideia central: interface = função do estado. A única pergunta de arquitetura aqui é: quem é o dono do estado? Vamos viver a evolução: lista fixa → setState na tela → controlador fora da tela.

Prática 1 — setState, o jeito rápido

Converta a tela para StatefulWidget (clique na classe → Cmd/Ctrl + . → Convert to StatefulWidget), torne a lista mutável e ligue o botão:

floatingActionButton: FloatingActionButton(
  onPressed: () => setState(
    () => _tarefas.add('Nova tarefa ${_tarefas.length + 1}'),
  ),
  child: const Icon(Icons.add),
),
Frase para gravar: “setState não desenha nada. Ele só avisa: mudou — roda o build() de novo.”

Prática 2 — estado fora da tela, o jeito que escala

class TaskController extends ChangeNotifier {
  final _tarefas = <String>['Instalar o Flutter', 'Rodar o primeiro app'];

  List<String> get tarefas => List.unmodifiable(_tarefas);

  void adicionar(String titulo) {
    if (titulo.trim().isEmpty) return;
    _tarefas.add(titulo.trim());
    notifyListeners(); // <- sem isto, a interface não fica sabendo!
  }

  void remover(String titulo) {
    _tarefas.remove(titulo);
    notifyListeners();
  }
}

A tela guarda o controlador, escuta com ListenableBuilder e só chama intenções:

body: ListenableBuilder(
  listenable: _controller,
  builder: (context, _) => ListView.builder(
    itemCount: _controller.tarefas.length,
    itemBuilder: (context, i) => TaskTile(title: _controller.tarefas[i]),
  ),
),

✅ Checkpoint do Módulo 2

Quiz rápido

1. Esqueci o notifyListeners(). O que acontece?

O dado muda, mas a interface não: o build() nunca roda de novo.

2. setState é errado?

Não! É o certo para estado local e passageiro (aba selecionada, campo aberto). Estado da funcionalidade e dos dados vai para o controlador.

3. Por que List.unmodifiable ao expor a lista?

Para ninguém burlar o controlador e mudar a lista sem avisar a interface.

Erros comuns

SintomaCausa provável
Toco e nada mudaFaltou setState/notifyListeners(), ou você mudou uma cópia da lista
setState() called after dispose()Controlador vivo depois que a tela fechou — faltou dispose()
A lista “volta” no Hot RestartEsperado: o estado está só na memória. Persistir é o próximo nível (Módulo 3)

Módulo 3 · Arquitetura e Organização 40 min · Sessão 2

Objetivo: transformar o “arquivo único que funciona” num projeto que outra pessoa consegue ler, testar e evoluir.
Resultado: o mesmo app por fora, organizado em camadas por dentro — com teste automatizado passando.

A ideia central: arquitetura para iniciantes não é um padrão famoso — é cada arquivo com um motivo para existir, e dependência numa direção só: features → state → data → models. Nunca o contrário.

A árvore alvo

lib/
  main.dart                        # só runApp()
  app.dart                         # MaterialApp + tema
  models/
    task.dart                      # Task (id, title, done, copyWith)
  data/
    task_repository.dart           # de onde as tarefas vêm
  state/
    task_controller.dart           # ChangeNotifier: add/toggle/remove
  features/tasks/
    tasks_page.dart                # a tela
    widgets/
      task_tile.dart               # widget "burro": dados + callbacks
      empty_state.dart
      add_task_dialog.dart

Refatoração guiada — 5 passos seguros

Regra de ouro: rode o app após cada passo. Nunca refatore no escuro — quebrou, o passo anterior é o seu resgate.

PassoMovaPara
1A classe Taskmodels/task.dart — sem importar Flutter!
2O TaskControllerstate/task_controller.dart
3A lista de tarefasdata/task_repository.dart — o controlador recebe o repositório no construtor
4Tema e MaterialAppapp.dart — o main.dart fica com ~5 linhas
5Tela e widgetsfeatures/tasks/ — o TaskTile só recebe dados e callbacks

O teste que prova o ponto

Com a regra fora da tela, dá para testar sem abrir interface nenhuma:

flutter test
# TaskController: addTask ignora título vazio · toggleTask marca e desmarca ✅
Frase para gravar: “se precisa abrir a tela para testar a regra, a regra mora no lugar errado.”

✅ Checkpoint do Módulo 3 (final!)

Quiz rápido

1. Amanhã as tarefas vêm de uma API. Quais arquivos mudam?

Só a camada data/ (um novo repositório) e onde ele é criado. Interface e modelo intactos.

2. O TaskTile pode chamar o controlador direto?

Não — widget “burro” recebe dados e callbacks. Quem conhece o controlador é a página. E “burro” aqui é elogio!

3. Organizar por tipo ou por funcionalidade?

Começamos por camadas para aprender os limites. Em projeto real: funcionalidade primeiro (features/tasks/widgets/…) — a árvore alvo já faz isso.
