Módulo 1 · Arquitetura e Organização 40 min

Objetivo: antes de escrever funcionalidades, entender o mapa do projeto — onde cada coisa mora e quem pode falar com quem.
Resultado: o mesmo app por fora, organizado em models / data / state / features por dentro.

A ideia central: arquitetura para iniciantes não é um padrão famoso — é cada arquivo com um motivo para existir, e dependência numa direção só: features → state → data → models. Nunca o contrário. Nos Módulos 2 e 3 você só vai preencher este mapa.

Módulo 2 · Gerenciamento de Estado 40 min

Objetivo: distinguir StatelessWidget de StatefulWidget, entender o state interno do widget (State + setState) e saber quando ele deve sair do widget e ir para um controller.
Resultado: app de tarefas funcionando — state local onde ele basta, e o estado da feature num TaskController fora da tela.

A ideia central: UI = função do estado. A única pergunta aqui é: quem é o dono do estado? A pasta state/, vazia desde o Módulo 1, ganha seu morador: tela lendo a fonte direto → setState na tela → controller fora da tela.

StatelessWidget × StatefulWidget — o state interno

Antes do estado do app, existe o estado que nasce e morre dentro de um widget:

StatelessWidgetStatefulWidget
State interno mutável?NãoSim, no objeto State
Mostra o quê?Só os parâmetros (final, imutáveis) que recebeParâmetros + fields do State
build() roda de novo quando…O pai reconstrói com nova configuraçãoO pai reconstrói ou ele chama setState()
No appTaskTile, EmptyStateTasksPage, AddTaskDialog
TasksPage (widget, imutável) ──createState()──▶ _TasksPageState (State, mutável)
   ↑ recriado a cada rebuild do pai               ↑ sobrevive aos rebuilds
   fields: só configuração (final)                  fields: o state interno

Ciclo de vida: createState() → initState() (crie controllers e subscriptions) → build() (puro, sem side effects) → didUpdateWidget() (nova configuração, mesmo State) → dispose() (libere tudo; depois daqui, setState() é erro). O State é preservado enquanto o widget estiver na mesma posição da widget tree (mesmo tipo e mesma Key) — por isso itens de lista com state precisam de ValueKey(task.id).

Dois níveis de estado:
Interno do widget (setState): local, efêmero, morre com ele — filtro ligado/desligado, texto digitado, aba selecionada.
Da feature (TaskController): compartilhado, testável, sobrevive à troca de tela — lista de tarefas, contador, loading/error.
Regra prática: não muda → Stateless · muda e só este widget usa → Stateful · mais de um usa ou é dado/regra → controller.

Repare: no app final, TasksPage é Stateful não porque a lista é state interno dela — a lista é do controller. Ela é Stateful para criar o controller no initState() e descartá-lo no dispose(): o State hospeda o ciclo de vida, e o ListenableBuilder reconstrói a UI quando o controller avisa.

Prática 1 — state interno com setState, o jeito rápido (para sentir o problema)

A tela vira StatefulWidget e ganha um filtro no State:

bool _mostrarConcluidas = true; // state interno: só esta tela usa, morre com ela

Switch(
  value: _mostrarConcluidas,
  onChanged: (valor) => setState(() => _mostrarConcluidas = valor),
)

Observe: o field vive no State, não no widget. Hot Reload mantém o filtro; Hot Restart volta ao valor inicial. Funciona — mas esse estado morreu dentro da tela: outra tela e os testes não enxergam nada. É essa dor que a Prática 2 resolve.

Frase para gravar: “setState não desenha nada. Ele executa a mudança, marca o widget como dirty e agenda o build() de novo no próximo frame. E ele só alcança o state interno deste widget — por isso a Prática 2 existe.”

Prática 2 — o controller em state/, o jeito que escala

class TaskController extends ChangeNotifier {
  TaskController(this._repository);

  final InMemoryTaskRepository _repository;

  List<Task> get tasks => _repository.getAll();
  int get pendingCount => tasks.where((t) => !t.done).length;

  void addTask(String title) {
    if (title.trim().isEmpty) return;
    _repository.add(Task(
      id: DateTime.now().microsecondsSinceEpoch.toString(),
      title: title.trim(),
    ));
    notifyListeners(); // <- sem isto, a UI não fica sabendo!
  }
  // toggleTask / removeTask: mesma ideia — muta via repository e avisa
}

A tela guarda o controller, escuta com ListenableBuilder e só chama methods:

body: ListenableBuilder(
  listenable: _controller,
  builder: (context, _) => ListView.builder(
    itemCount: _controller.tasks.length,
    itemBuilder: (context, i) {
      final task = _controller.tasks[i];
      return TaskTile(
        task: task,
        onToggle: () => _controller.toggleTask(task.id),
        onDelete: () => _controller.removeTask(task.id),
      );
    },
  ),
),

Módulo 3 · Consumo de API e Async 40 min · Sessão 2

Objetivo: buscar as tarefas de uma API real e tratar os três states de todo fluxo assíncrono: loading, error e success.
Resultado: tarefas vindas da internet (JSONPlaceholder), com spinner e “tentar de novo” — e a UI praticamente intacta.

A ideia central: dado que vem da rede demora e pode falhar. Quem busca é data/; quem expõe o estado é state/; a UI só desenha. É a ordem do treinamento se pagando: arquitetura isolou a fonte, estado isolou a reação.

A API do treinamento

JSONPlaceholder — API pública de mentirinha, perfeita para treinar:

GET https://jsonplaceholder.typicode.com/todos?_limit=10
→ [ { "id": 1, "title": "delectus aut autem", "completed": false }, ... ]
Sem internet no local? Plano B: o mesmo repository em memória com Future.delayed(const Duration(seconds: 1)). Todo o resto funciona igual — async é async.

Prática 1 — a fonte nova mora em data/

// no terminal:  flutter pub add http

// models/task.dart — a tradução do JSON
factory Task.fromJson(Map<String, dynamic> json) {
  return Task(
    id: json['id'].toString(),
    title: json['title'] as String,
    done: json['completed'] as bool? ?? false,
  );
}
// data/task_repository.dart — o mesmo contract, outra fonte
class ApiTaskRepository {
  Future<List<Task>> fetchTasks() async {
    final response = await http.get(
      Uri.parse('https://jsonplaceholder.typicode.com/todos?_limit=10'),
    );
    if (response.statusCode != 200) {
      throw Exception('Falha ao buscar tarefas (${response.statusCode})');
    }
    final List<dynamic> data = jsonDecode(response.body);
    return data.map((e) => Task.fromJson(e as Map<String, dynamic>)).toList();
  }
}

Prática 2 — os 3 states, no controller e na tela

// state/task_controller.dart
Future<void> loadTasks() async {
  isLoading = true;
  errorMessage = null;
  notifyListeners();
  try {
    _tasks = await _apiRepository.fetchTasks();
  } catch (_) {
    errorMessage = 'Não foi possível carregar as tarefas.';
  } finally {
    isLoading = false;
    notifyListeners();
  }
}
// na tela, a ordem dos ifs É a aula:
if (_controller.isLoading && _controller.tasks.isEmpty) {
  return const Center(child: CircularProgressIndicator()); // loading
}
if (_controller.errorMessage != null && _controller.tasks.isEmpty) {
  return /* mensagem + botão "Tentar de novo" */;             // erro
}
if (_controller.tasks.isEmpty) return const EmptyState();
return /* a mesma lista do Módulo 2 */;                       // success
